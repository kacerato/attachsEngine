# API Save por projeto — 2026-09-30

## Capacidade real e referências

SaveStore persiste string, bool, int64 e double finito; remove chaves; grava/lê/deleta arquivos UTF-8 estritos e binários; flush atômico com snapshot anterior e recuperação compatível. Behavior.Save usa o store configurado pelo host. SaveStore também pode ser aberto diretamente fora de Play, com raiz explícita de projeto existente.

Referências oficiais: [Unity 6.0 PlayerPrefs](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/PlayerPrefs.html), [Unity 6.0 Application.persistentDataPath](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Application-persistentDataPath.html), [Godot 4.5 FileAccess](https://docs.godotengine.org/en/4.5/classes/class_fileaccess.html). Princípios extraídos: persistência entre sessões, área de dados separada da autoria, valores simples tipados e arquivos para checkpoints. Astra adapta o escopo para **projeto**: `.astra/save`, enquanto PlayerPrefs usa localização global por aplicação/plataforma e Godot usa `user://`. Não há alias PlayerPrefs nem promessa de storage global do Android exportado.

## Ownership e lifecycle

NativeBehaviorRuntime recebe a raiz que já usa NativeCompiler.LoadApplied; abre SaveStore nessa raiz, entrega a BehaviorWorld.Start e fecha após Stop. Diretório inválido, inacessível ou incompatível falha explicitamente: não usa diretório temporário alternativo. BehaviorWorld aceita store opcional do host; acesso Save sem configuração ou Behavior destacado lança erro. O store passado é emprestado: BehaviorWorld.Flush no encerramento e SaveStore.Dispose pelo seu dono. Arquivos e valores permanecem após sair de Play e reabrir o projeto. Coroutines normais podem acessar Save; o store também serializa chamadas concorrentes por lock. Um lease de arquivo exclusivo bloqueia dois SaveStores escritores simultâneos para o mesmo projeto; não existe merge concorrente silencioso.

## Contrato de dados e falhas

Chaves SetString/SetBoolean/SetInt64/SetDouble ficam na memória até Flush/Dispose; Contains/Delete e Get tipado consultam esse snapshot. Ausência retorna fallback informado; tipo incorreto lança InvalidDataException. Não há coerção entre int64/double/string. Strings usam UTF-8 estrito; números não finitos são recusados. Arquivos WriteText/WriteBytes são publicados imediatamente por substituição atômica.

Limites: 4096 chaves, chave 128 bytes UTF-8, string 16 KiB, snapshot serializado 256 KiB, arquivo 1 MiB, namespace files 16 MiB e 1024 arquivos. ReadBounded verifica tamanho antes de alocar, lê exatamente e recusa crescimento após snapshot. Varredura para quota é limitada a 2048 entradas e profundidade 16; não segue links. Paths de arquivos aceitam `/`, máximo 512 caracteres e 16 segmentos, rejeitam absoluto, `..`, `.` e segmentos vazios, backslash, ADS/colon, nomes de dispositivo Windows, caracteres de controle e finais ponto/espaço. Todos os ancestrais e arquivos existentes são checados contra symlinks/reparse points, incluindo raiz e arquivos internos.

O host assume exclusividade da área de save enquanto usa o lease. Checagens de filesystem protegem links existentes e operações usuais; as APIs portáveis .NET não oferecem garantia de handle relativo/no-follow contra troca maliciosa simultânea de diretórios por processo externo. Esta fronteira não é um sandbox de código C# arbitrário: um script com System.IO pode acessar outros paths. Não há criptografia ou sincronização cloud.

Flush escreve arquivo temporário único no mesmo diretório, Flush(true), depois File.Replace com `values.previous.json` quando existe snapshot corrente; primeira gravação usa rename. Falha remove somente o temporário próprio e é propagada. Ao abrir snapshot truncado/inválido ou ausente, um backup válido versão 1 recupera dados, com Recovery=PreviousSnapshot explícito. Versão não suportada lança SaveVersionException e não volta silenciosamente para versão antiga. Falha de recuperação impede abrir o store. Durabilidade de diretório/power loss depende do filesystem; não há alegação de fsync-directory portátil.

## Uso

```csharp
Save.SetInt64("checkpoint", 4);
Save.SetBoolean("tutorial_done", true);
Save.WriteText("slots/main.json", "{\"level\":4}");
Save.Flush();
long checkpoint = Save.GetInt64("checkpoint", 0);
```

Fora de Play: `using var store = new SaveStore(projectRoot);` seguido dos mesmos métodos. Não armazene save na pasta de scripts/assets.
